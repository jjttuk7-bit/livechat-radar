## 0. 전환 사유 (Why Pivot)

라이브 쇼핑 전용으로 완주했지만 **시장의 데이터 밀도가 제품을 지탱하지 못한다**.

| 항목 | 라이브 쇼핑 (AS-IS) | 정치·시사 (TO-BE) |
|------|--------------------|-------------------|
| 실시간 동시 시청자 | 대부분 100명 미만 | 1,000명 이상 흔함 |
| 추정 분당 댓글(CPM) | 20~40 | **200~600** |
| 방송 1회 총 댓글 | 1,000~2,400 (1시간) | **40,000~60,000 (3시간)** |
| 방송 빈도 | 비정기 (주 1~2회) | **거의 매일, 고정 시간대** |
| 시청자 재방문 | 낮음 (구매 목적 단발) | **매우 높음 (충성 고정 시청층)** |
| 통계 유의성 | 표본 부족 → 분석 무의미 | 충분 |

**핵심 진단:** 이 제품의 모든 기능(6축 태깅 분포, 온도 지표, 타임라인 추이, 시청자 프로필 누적)은 **댓글 수가 통계적으로 유의미할 때만 작동한다.** 동접 100명 미만에서 CPM 20이면 40초 분석 윈도우에 댓글 13건 — 분포도, 추이도, 프로필도 노이즈다. 제품이 잘못된 게 아니라 **시장의 데이터 밀도가 잘못 매칭됐다.**

정치·시사는 세 가지가 동시에 성립한다:
1. **데이터 밀도** — 모든 집계 지표가 즉시 유의미해짐
2. **매일 방송** — 크로스세션 누적 분석(회차 비교·아젠다 추이)이 처음으로 가능
3. **고충성도 고정 시청층** — `author` 단위 프로필이 세션 내 집계를 넘어 **진짜 단골 인식**으로 격상

### 0-1. 전환 결정 요약

| 항목 | AS-IS | TO-BE |
|------|-------|-------|
| 제품 정체성 | 유튜브 라이브 쇼핑 AI 판매 조연출 | **유튜브 정치·시사 라이브 AI 진행 조연출 + 채널 방어 레이더** |
| 분석 단위 | 상품(SKU) × 옵션 | **이슈/아젠다 × 인물** |
| 핵심 가치 | "지금 무슨 말을 해서 무엇을 팔까" | "지금 **시청자가 가장 듣고 싶은 사안**은 무엇이고, **채널을 위험하게 하는 댓글**은 무엇인가" |
| 수익 KPI | 구매 전환 (판매 건수) | 슈퍼챗·멤버십·구독·체류 |
| 최대 기술 과제 | 없음 (저volume) | **고CPM 처리 파이프라인 + YouTube API 쿼터** |
| 신규 킬러 기능 | 미응답 질문 큐 | **리스크·모더레이션 레이더** (채널 제재 방어) |

## 1. 제품 비전 & 핵심 사용자

**한 줄 비전:** 정치·시사 라이브 진행자 옆에서 "지금 수백 개씩 쏟아지는 채팅에서 시청자가 진짜 듣고 싶은 사안이 무엇이고, 어떤 댓글이 채널을 위험하게 하는지"를 실시간으로 추출해 처방하는 AI 조연출.

**핵심 사용자 (1차):** 1인~소규모 정치·시사 유튜브 채널의 **진행자 + 모더레이터**. CPM 300짜리 채팅창은 인간이 읽는 것이 물리적으로 불가능하다 — 스크롤 속도가 읽는 속도를 넘는다. 라이브 쇼핑에서는 "놓친 질문"이 페인이었지만, 정치·시사에서는 **채팅창 자체가 블랙박스**인 것이 페인이다.

**대표 시나리오:**
- 진행자가 A 사안을 15분째 다루는데 채팅은 이미 B 사안으로 옮겨감 → "B 관련 요구 87건 급상승, 지금 전환 권장"
- 특정 인물에 대한 명예훼손 소지 단정 표현이 급증 → **"댓글창 리스크 경고: 해당 표현 42건. 슬로우 모드 + 진행자도 단정 표현 자제 권장"**
- 근거 자료 요청이 몰림 → "원문 자료 화면 공유 요구 34건"
- 결집 온도가 피크에 도달 → "지금 구독·후원 안내 적기 (직전 30초 대비 +140%)"
- 미확인 주장이 채팅에서 확산 → "확인 안 된 내용이 돌고 있습니다" 처방 멘트 (**AI가 진위 판정은 하지 않음**)
- 방송 종료 → 아젠다별 반응 랭킹 + 골든 모먼트 + **다음 방송 아젠다 추천** + 어제 회차 대비 결집도 비교

## 2. 안전·윤리 설계 결정 (선행 제약)

이 섹션은 뒤 모든 설계를 제약한다. 정치 도메인은 쇼핑과 달리 **잘못 만들면 제품이 곧 리스크**가 된다.

| # | 결정 | 이유 |
|---|------|------|
| **D-1** | **개인 단위 정치성향 라벨링 미도입.** 특정 시청자를 "보수/진보/○○당 지지"로 태깅·저장·나열하는 기능은 만들지 않는다. | 정치적 견해는 개인정보보호법상 **민감정보**. 닉네임과 함께 성향 명단을 만드는 것은 법적·윤리적으로 방어 불가 |
| **D-2** | 시청자 개인 단위 지표는 **비민감 축만** — 참여 빈도, 후원 여부, 출석 연속일, 미응답 질문 보유, (행위 기준) 도배·욕설 여부 | 충성도·모더레이션은 성향 정보 없이 성립 |
| **D-3** | 여론 분포는 **집계 단위로만** 표시 (동의/반대/의심 비율). 개인으로 역추적하는 UI를 제공하지 않음 | 집계는 진행에 필요, 개인 지목은 불필요 |
| **D-4** | **AI는 팩트체크 판정을 하지 않는다.** `misinfo_suspect`는 "검증 필요 주장" 플래그까지만. "거짓" 라벨 출력 금지 | LLM 오판정의 결과가 명예훼손·허위정보 확산 양방향으로 심각 |
| **D-5** | 선거법 관련은 **주의 신호 + 면책 문구**만. 위법 여부 판정 금지 | 공직선거법 해석은 법률 판단 영역 |
| **D-6** | 상대 진영 공격 멘트 생성, 좌표·조직적 결집 유도, 여론 조작 목적 기능은 **범위 외**. 처방 멘트는 자기 채널 진행 품질(설명·근거 제시·질문 응답·후원 안내)에 한정 | 제품 정체성을 "진행 보조 + 채널 방어"로 못박음 |
| **D-7** | evals에 **좌우 대칭 fixture 쌍** 도입 — 구조가 동일하고 진영만 반대인 입력에 대해 리스크 판정·처방 톤이 대칭인지 회귀 검증 | 프롬프트·시뮬레이터 사전의 정치 편향 회귀 방지 |
| **D-8** | 크로스세션 저장 시 닉네임은 **해시 + 보존기간 정책**(기본 90일) 적용, 원문 댓글 장기 보관 최소화 | P-9 저장소 도입 시 필수 |

> D-1/D-2가 G-1 핫리드 보드의 정치 버전 설계를 바꾼다: 쇼핑의 "구매 가능성 점수"는 그대로 옮길 수 없고, **"충성·참여 점수"(비민감)** 로 재정의한다.

## 3. 분석 체계 — 6축 × 37태그 Taxonomy

쇼핑의 6축 구조를 **그대로 유지**하고 의미만 교체한다. 축 개수·태그 개수를 맞추면 `TAG_AXIS` 맵, `AxisDistribution` 컴포넌트, strict 스키마 enum 구조, 시뮬레이터 골격이 전부 재사용된다.

### 축 1. 아젠다·이슈 (`agenda`) — 무엇에 대해 말하는가
| 태그 | 의미 |
|------|------|
| `issue_mention` | 특정 사안 언급 |
| `figure_mention` | 특정 인물·기관 언급 |
| `topic_request` | "이 주제 다뤄주세요" |
| `followup_request` | 지난 방송 후속 요청 |
| `source_request` | 근거·자료·원문 요청 |
| `guest_request` | "○○ 초대해주세요" |
| `breaking_tip` | 제보·속보 공유 |

### 축 2. 반응·의견 (`stance`) — 집계 전용 (D-1/D-3)
| 태그 | 의미 |
|------|------|
| `agree_support` | 동의·지지 |
| `disagree_object` | 반대·이견 |
| `doubt_verify` | 의심·검증 요구 |
| `mixed_nuance` | 조건부·양비 |
| `whataboutism` | 화제 전환·맞불 (논쟁 격화 선행 신호) |

> **진영 라벨(보수/진보/정당)은 태그에 존재하지 않는다.** 여론 흐름은 위 5태그의 집계 비율로만 표현.

### 축 3. 정서·온도 (`emotion`)
| 태그 | 의미 |
|------|------|
| `outrage` | 분노·격앙 |
| `anxiety` | 불안·우려 |
| `ridicule` | 조소·비꼼 |
| `hope_cheer` | 환호·응원 |
| `fatigue_disengage` | 피로·지루함 (이탈 선행 신호) |
| `despair` | 실망·체념 |

### 축 4. 질문·요구 (`inquiry`) — 미응답 큐 적재 대상
| 태그 | 의미 |
|------|------|
| `factual_question` | 사실 확인 질문 |
| `explain_request` | "쉽게 설명해주세요" |
| `opinion_request` | 진행자 견해 요청 |
| `host_question_direct` | 진행자 지목 질문 |
| `rerun_request` | 다시보기·타임스탬프 요청 |
| `how_to_act` | "우리가 뭘 해야 하나" 행동 문의 |

### 축 5. 참여·후원 (`loyalty`) — 수익 엔진
| 태그 | 의미 |
|------|------|
| `superchat` | 슈퍼챗·후원 |
| `membership` | 멤버십 가입·갱신 |
| `subscribe_share` | 구독·좋아요·공유 독려 |
| `attendance` | 출근/출석 도장·인사 (정치 채널 특유의 강한 신호) |
| `community_bond` | 시청자 간 유대·응원 |
| `petition_action` | 청원·집회·투표 등 오프라인 행동 언급 → 선거법 주의와 연동 |

### 축 6. 리스크·운영 (`risk`) ★ 정치 채널 킬러 축
| 태그 | 의미 | 처방 |
|------|------|------|
| `hate_slur` | 혐오·차별·욕설 | 삭제/차단 권고 |
| `defamation_risk` | 명예훼손 소지 (단정적 범죄 단언) | **채널 법적 리스크 경고** |
| `misinfo_suspect` | 미확인 주장 확산 | 검증 필요 플래그 (**판정 아님** — D-4) |
| `election_law_watch` | 선거 관련 주의 표현 | 선거기간 모드에서 활성 (**판정 아님** — D-5) |
| `brigading_spam` | 조직적 도배·좌표 | 슬로우 모드·모더레이터 알림 |
| `stream_issue` | 음향/화면/끊김 | 기술 확인 |
| `other` | 미분류 | — |

**총 6축 × 37태그** (쇼핑과 동일한 규모 → 구조 호환).

## 4. 고CPM 처리 파이프라인 ★ 최대 신규 과제

쇼핑에는 없던 문제다. 현재 구조는 **저volume 전제로만 성립**한다.

### 4-1. 현재 구조의 붕괴 지점

| 지점 | 현재 코드 | CPM 300에서 무슨 일이 나는가 |
|------|-----------|------------------------------|
| 분석 윈도우 | `server.ts` `messages.slice(-80)` | 40초 주기에 신규 댓글 ~200건인데 80건만 봄 → **60% 유실** |
| 리포트 표본 | `messages.slice(0, 150)` | 3시간 54,000건 중 **방송 도입부 150건만** 분석 → 리포트가 사실상 무의미 |
| 응답 캐시 키 | 메시지 ID 전량 SHA1 | 매 호출 ID 집합이 전부 바뀜 → **캐시 히트율 0** |
| 프론트 메시지 배열 | `messages` 무한 누적 | 54,000개 React 상태 + 리스트 렌더 → 브라우저 정지 |
| AI 비용/지연 | 전량 원문 직렬화 | 입력 토큰이 CPM에 비례해 선형 증가 |

### 4-2. TO-BE: 3계층 파이프라인

```
[모든 댓글 100%]
   │
   ├─ L1  로컬 프리필터 (비용 0, 전량)              ← src/lib/prefilter.ts (신규)
   │    · 인물/이슈 키워드 사전 매칭 → 아젠다 카운트
   │    · 혐오·욕설·단정표현 사전 → 리스크 1차 탐지
   │    · 동일/유사 텍스트 클러스터링 → dedupe (대표 1건 + count n)
   │    · 슈퍼챗/멤버십 이벤트 추출, CPM·스파이크 계산
   │    · 도배 탐지 (동일 author 반복 / 동일 문구 확산 속도)
   │    → 산출: 집계 통계 + 리스크 후보 + 대표 댓글 풀
   │
   ├─ L2  AI 정밀 태깅 (표본 + 타깃)                ← /api/analyze/talk
   │    · 층화 표본(stratified): 각 축·클러스터에서 대표 추출 60~100건
   │    · 타깃 전수: L1이 플래그한 리스크 후보 + 질문 후보는 누락 없이 포함
   │    → 산출: analyses[] (샘플에 대한 정밀 6축 태깅)
   │
   └─ L3  처방 생성                                  ← 동일 호출 내
        · 입력 = L1 집계 통계 + L2 표본 + 큐시트 컨텍스트
        · 산출: metrics / actionCards / unanswered / agendaInterest
                / riskAlerts / recentSummary / hostAdvice
```

**핵심 전환:** AI 입력이 "댓글 원문 전량"에서 **"집계 통계 + 대표 표본"** 으로 바뀐다. 이로써 호출당 입력 토큰이 CPM과 무관하게 **상수로 고정**된다. 정치 채널의 복붙 구호 문화 덕에 dedupe 압축률이 높을 것으로 예상되며(실측 필요), 이는 표본 품질에 오히려 유리하다.

### 4-3. 부수 변경 사항

- **캐시 키:** ID 전량 해시 → `(방송ID, 10초 버킷 타임스탬프, L1 통계 시그니처)`
- **리포트:** `slice(0, 150)` 폐기 → 방송 전체를 5분 버킷으로 나눈 **층화 표본 + L1 전량 집계치**를 함께 전달
- **프론트 상태:** `messages` 무한 누적 → **최근 N건 링버퍼(표시용) + 누적 카운터(집계용) 분리**. 피드는 가상 스크롤
- **수집:** `streamList` 전환 (4-4 참조). 폴링을 유지하는 경우에만 `pollingIntervalMillis` 준수 + `maxResults` 명시 + 적응형 간격

### 4-4. YouTube 채팅 수집 방식 전환 — `list` 폴링 → `streamList` ★

**조사 결과 (2026-08-12 공식 문서 확인):**

1. **`liveChatMessages.streamList`가 존재하며, 공식 문서가 폴링 대신 이 방식을 권장한다.**
   > "To poll for live chat messages, use the `liveChatMessages.streamList` method. The `streamList` method pushes new messages to the client as they become available, which reduces the need for constant polling." — [liveChatMessages.list 문서](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/list)

   - **서버 스트리밍 연결** — 새 메시지를 클라이언트로 push (long-lived HTTP)
   - 파라미터: `liveChatId`, `part`(id/snippet/authorDetails), `maxResults`(200~2000, **기본 500**), `profileImageSize`, `pageToken`
   - **끊김 복구:** 마지막 `nextPageToken`을 `pageToken`으로 재연결하면 그 지점부터 재개 → 유실 없음
   - 응답에 `offlineAt`(방송 종료 시각), `activePollItem`(진행 중 투표) 포함 → **투표 기능은 정치·시사에서 직접 쓸 수 있는 보너스 데이터**

2. **`liveChatMessages.list`의 유닛 비용은 공식 쿼터 표에 아예 없다.** 확인한 사실:
   - [공식 쿼터 표](https://developers.google.com/youtube/v3/determine_quota_cost)에 liveChat·liveBroadcast·liveStream·superChatEvents **어떤 행도 없음**. "Live Streaming API 메서드도 쿼터를 소비한다"는 문장만 있고 수치 없음
   - 웹의 2차 자료는 **1 유닛과 5 유닛으로 서로 모순** → 신뢰 불가
   - **결론: 이전 기획서의 "5 유닛 가정"은 근거 없음.** 실측으로만 확정 가능

3. **현재 코드는 `maxResults`를 아예 지정하지 않는다** (`server.ts` chat 엔드포인트). 기본 500이므로 CPM 300에서도 배치 용량 자체는 충분했다 — 유실 원인은 API가 아니라 **분석 단계의 `slice(-80)`**이었다.

**전환 후 구조:**

| 항목 | AS-IS | TO-BE |
|------|-------|-------|
| 수집 방식 | 클라이언트가 3.5초마다 `/api/youtube/chat` 폴링 | **서버가 `streamList` 스트림 1개 유지**, 클라이언트로 push |
| 시간당 API 호출 | ~1,029회 | **연결 1회 + 재연결 시에만** |
| 유실 위험 | pageToken 관리 실패 시 발생 | `nextPageToken` 재개로 원천 차단 |
| 쿼터 노출 | 폴링 횟수에 선형 비례 | 연결 수에 비례 (대폭 감소 예상) |

**⚠️ 배포 아키텍처 충돌 (신규 발견):** `streamList`는 long-lived 연결을 요구하는데, 현재 배포는 **Vercel Serverless(E-0)** 다 — 함수 실행 시간 상한 때문에 3시간 스트림을 유지할 수 없다. 대응 선택지:
- (a) 수집 워커만 상시 실행 환경으로 분리 (Railway / Fly.io / VPS) + 대시보드는 Vercel 유지
- (b) 클라이언트가 직접 `streamList` 연결 (API 키 노출 문제 → 불가)
- (c) `list` 폴링 유지 + `maxResults` 명시 + 적응형 간격 (쿼터 실측 후 판단)

> **P-0 검증 항목으로 재정의:** "쿼터 증량 신청"이 아니라 **① 실측으로 유닛 비용 확인(Cloud Console 쿼터 지표) → ② `streamList` 도입 가능성 + 상시 실행 환경 필요성 판단**. 증량 신청은 실측 후에도 부족할 때의 수단으로 내린다.

## 7. 신규 핵심 패널: 리스크·모더레이션 레이더 ★

쇼핑의 "미응답 질문 큐"에 대응하는 **정치 버전의 킬러 기능**. 채널 운영자의 실질적 최대 공포는 "질문 놓침"이 아니라 **채널 제재·법적 분쟁**이다.

- `risk` 축 태그 댓글을 심각도순 큐로 적재
- 각 항목: 원문 · 유형 · 심각도 · 권고 조치(삭제 / 차단 / 관망) · 확산 정도(동일 문구 n건)
- **집계 경고 배너:** 리스크 지수가 임계 초과 시 상단 전체 폭 경고 + 슬로우 모드 권장
- **진행자 자기 경고:** 채팅 리스크가 높은 사안은 진행자 발언도 위험 → "이 사안은 단정 표현 자제" 카드
- 모더레이터 협업: 처리 완료 체크(수동) → 큐에서 제거. 미처리 경과 시간에 따라 심각도 상승
- **면책 문구 상시 표시:** "본 판단은 참고용이며 법적 판정이 아닙니다" (D-4/D-5)

> 1차는 **탐지·권고만**. YouTube 채팅 삭제/차단 API 자동 실행은 OAuth + 오탐 리스크로 인해 범위 외 (P-12 이후 검토).

### 우선순위 (ROI 순)

```
0순위 (착수 전 검증 — 여기서 막히면 전부 무의미)
└─ P-0 쿼터 유닛 실측 → streamList 전환 판단 → 실행 환경 결정

1순위 (MVP — "채팅 블랙박스 해소 + 채널 방어")
├─ P-1 타입/스키마
├─ P-2 L1 파이프라인          ← 고CPM 없이는 아무것도 성립 안 함

├─ P-5 UI 코어
├─ P-6 ★ 리스크 워치           ← 최대 차별화
└─ P-10 프론트 성능(일부)      ← 실사용 즉시 필요, 후순위로 밀 수 없음

2순위 (진행 품질 + 수익)
├─ P-7 아젠다 레이더
├─ P-8 후원·충성 + 어필 윈도우
└─ P-9 타임라인/리포트

3순위 (자산화)
```
